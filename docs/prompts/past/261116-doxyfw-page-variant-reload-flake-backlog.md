## BL-001 起動直後の Chrome で、文書の開始時の削除の後に保存した localStorage の値が再読み込みで失われる理由が未確認

### 概要と問題点

- **現状の事象**: `puppeteer.launch()` で起動した直後の Chrome で、最初のページの文書の開始時に `localStorage.removeItem()` を実行し、その後に同じキーへ保存して `page.reload()` を行うと、CPU の負荷が高いときに保存値が失われます。失われた値は、同じブラウザーで開き直したページでも読めません。Oracle Linux 8.10 の Chrome for Testing 153.0.8010.36 (headless)、puppeteer 25.11.0、`file://` のページで確認しました。CPU を 2 コアに絞り、空ループ 4 本で負荷をかけた状態で、60 回中 24 回発生しました。削除を行わない場合は、60 回とも発生しませんでした。削除スクリプトは、再読み込みでは再実行されていません。同じ負荷の下で、最初の文書で書いた `sessionStorage` の値が再読み込み後に読めない回も、200 回中 4 回ありました。Chrome の内部でなぜ値が失われるか (保存領域の実装の不具合か、仕様か) は、確認していません。
- **本来あるべき姿**: 値が失われる理由と、発生する条件の範囲 (ほかの版の Chrome、`http://` のページ、`sessionStorage`) が分かっていること。不具合であれば、Chromium の不具合報告の有無が分かっていること。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討 ID: 261116-doxyfw-page-variant-reload-flake。CI の不定期な失敗の原因の切り分けで判明)。
- **今回の見送り理由**: 案件の目的 (CI の不定期な失敗をなくす) は、テストが問題の条件を満たさないようにする修正で達成できます。理由の追究には、Chromium のソースの調査や不具合報告の検索が必要で、テストの安定化とは別の作業量になります。影響を受けるテストは 1 件だけで、製品のレポート本体は同じ条件を持ちません。
- **継続作業での経緯と対処**: 2026-11-25 に継続案件 `261125-doxyfw-storage-loss-investigation-overview.md` (検討 ID: 261125-doxyfw-storage-loss-investigation) を開始し、状態を「検討中」にしました。調査の範囲、記録先、Chromium への報告の扱い、時間の上限を、検討用 Markdown ([261125-doxyfw-storage-loss-investigation-discussion.md](../current/261125-doxyfw-storage-loss-investigation-discussion.md)) の Q-001 から Q-009 で確認中です。事前の確認として、Chromium の不具合トラッカーの既知報告を検索しましたが、この現象に該当する報告は見つかりませんでした。2026-11-25 20:35 に Q-001 から Q-009 の回答を受け、次の方針で合意しました。調査を実施し、Chrome for Testing 153.0.8010.36 と取得時点の Stable の最新版 (2026-11-25 時点で 158.0.8127.88) の 2 つの版、`file://` と `http://` のページ、文書の開始時の削除と読み込み完了後の削除 (対照として削除なし) を比較します。`sessionStorage` も調査に含めます。試行回数は、`localStorage` で削除を伴う条件を 60 回 (発生しなければ 200 回まで追加)、そのほかを 200 回とします。調査は再現実験までとし、Chromium のソース読解は行いません (内部の原因は継続案件の残課題一覧へ記録)。調査報告はこの項目と継続案件の文書に記録し、正本文書は変更しません。外部への不具合報告は送信せず、下書きを調査報告に含めます。2026-11-25 20:54 に追加の Q-010 と Q-011 の回答を受け、再現スクリプトはセッションの一時ディレクトリにだけ置き (最小の再現コードは調査報告に掲載)、`sessionStorage` は 1 回ごとに起動する方式とブラウザーを使い回す方式の両方で調べることで合意しました。2026-11-25 20:57 に最終仕様 `261125-doxyfw-storage-loss-investigation-design.md` を作成し、状態を「対応中」にしました。確定した方針は、上記の条件 (版 2 つ、ページ 2 種類、削除の時点 3 条件、`sessionStorage` は起動方式 2 つ。合計 36 条件) を既知の負荷の下で再現実験し、結果と報告用の下書きを最終仕様の「調査結果」の章に記録することです。 2026-11-26 01:57 から 03:56 に、153.0.8010.36 と 158.0.8127.88 (Stable) で 36 条件、有効な試行 6,920 回 (例外 0 件) を実施し、状態を「完了」にしました。結論の要約は次のとおりです。値が失われたのは、文書の開始時に削除した条件で、かつ `file://` のページに限られ、`localStorage` (153 で 60 回中 32 回、158 で 60 回中 30 回)、`sessionStorage` の 1 回ごとに起動 (200 回中 89 回、96 回)、同じく使い回し (200 回中 62 回、63 回) のすべてで発生しました。`http://` のページ、読み込み完了後の削除、削除なしでは、200 回中 0 件でした。版による違いはなく、Stable でも解消していません。既知の不具合報告は見つからず (WebSearch 4 回)、`page_link_probe.js` は変更していません。詳細と最小の再現コード、報告用の下書きは、`261125-doxyfw-storage-loss-investigation-design.md` の「調査結果」の章を参照してください。Windows での発生有無、内部の原因、以前の観測 (削除なしの `sessionStorage` の使い回しで 200 回中 4 回) の再現性は未確認で、継続案件の残課題一覧 (`261125-doxyfw-storage-loss-investigation-backlog.md`) に転記しました。

### 影響範囲とリスク

- **影響対象**: puppeteer で `localStorage` または `sessionStorage` を扱うテスト。現在、`framework` 配下の `bin_test` で `localStorage` の `removeItem` を使うのは、`framework/doxyfw/bin_test/page_link_probe.js` だけです。
- **放置した場合のリスク**: 同じ条件を持つテストを将来書くと、負荷の高い CI で不定期に失敗します。`sessionStorage` についても同様の現象を観測しているため、起動直後のブラウザーで保存領域へ書き込むテストは、同じ失敗を起こすおそれがあります。

### 推奨される対応策

- **恒久対応案**: 最小の再現手順 (1 回ごとにブラウザーを起動し、文書の開始時に `removeItem` を実行してから保存と再読み込みを行う) を使い、Chrome の版、ページの種類 (`file://` と `http://`)、削除の時点 (文書の開始時と読み込みの完了後) を変えて、発生する条件の範囲を調べます。Chromium の不具合報告を検索し、該当があれば `page_link_probe.js` のコメントへ `see: <URL>` を追加します。該当がなければ、報告するかを判断します。
- **参考情報**: `framework/doxyfw/bin_test/page_link_probe.js` の `newReportPage()`。対策元の残課題一覧 `app/porter/docs/prompts/past/261115-porter-multicast-src-contract-backlog.md` の BL-003。
