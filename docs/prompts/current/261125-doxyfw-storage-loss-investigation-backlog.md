## BL-001 Chrome の内部で保存領域の値が失われる原因 (ソース読解による解明) が未確認

### 概要と問題点

- **現状の事象**: 再現実験で、文書の開始時に `removeItem` を実行したときに限り、`file://` のページで `localStorage` と `sessionStorage` の保存値が再読み込みで失われることを確認しました (Chrome for Testing 153.0.8010.36 と 158.0.8127.88、CPU 2 コアに空ループ 4 本の負荷。`localStorage` は 60 回中 30 から 32 回、`sessionStorage` は 200 回中 62 から 96 回)。`http://`、読み込み完了後の削除、削除なしでは 0 件でした。Chrome の内部でなぜ値が失われるか (保存領域の実装の不具合か、仕様か) は、確認していません。推測として、文書の開始時の `removeItem` が保存領域の読み込みの完了前に実行されると、その後の保存が永続化されない可能性があります (未検証)。
- **本来あるべき姿**: 値が失われる内部の原因が分かっていること。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (Q-009 の回答。2026-11-25)。2026-11-26 に再現実験を完了し、発生条件の範囲を最終仕様の「調査結果」の章に記録した。
- **今回の見送り理由**: Chromium のソース読解は終わりが見えにくく、発生条件の範囲の把握は再現実験で達成できたため。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: puppeteer で `file://` のページの保存領域を、文書の開始時に削除するテスト。
- **放置した場合のリスク**: 回避策 (読み込み完了後に削除) は分かっていますが、Chrome の版の更新で条件が変わった場合に、再度の切り分けが必要になります。

### 推奨される対応策

- **恒久対応案**: 最終仕様の「調査結果」の章の最小の再現コードを使い、Chromium の DOM Storage の実装で、`file://` の保存領域の読み込みと、文書の開始時の削除の反映の順序を調べます。外部へ報告する場合は、同章の報告用の下書きを使います (報告の送信はユーザーが別途判断)。
- **参考情報**: 対策元 `261116-doxyfw-page-variant-reload-flake-backlog.md` の BL-001。

## BL-003 以前の観測 (削除なしの sessionStorage の使い回しで 200 回中 4 回) が今回の実験で再現しない

### 概要と問題点

- **現状の事象**: 対策元 BL-001 の既知の事実として、同じ負荷で、ブラウザーを使い回す最小の再現用スクリプトで、最初の文書で書いた `sessionStorage` の値が再読み込み後に読めない回が 200 回中 4 回ありました。今回の実験では、`sessionStorage` の使い回しで削除なし (条件 3) の `file://` と `http://` は各 200 回で 0 件でした。以前の観測のスクリプトは保存されておらず、手順の差 (新しいページでなく最初のページを使う、保存と再読み込みの間隔など) は特定できていません。
- **本来あるべき姿**: 以前の観測の原因 (手順の差か、ほかの要因か) が分かっていること。

### 経緯と見送り理由

- **摘出契機**: 今回の実験の結果と対策元 BL-001 の既知の事実の食い違い (2026-11-26)。
- **今回の見送り理由**: 以前のスクリプトが残っておらず、範囲外の追加実験が必要になるため。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: 起動直後のブラウザーの最初のページで `sessionStorage` を使うテスト。
- **放置した場合のリスク**: 削除を伴わない手順でも発生する条件があった場合、回避策が不足するおそれがあります。

### 推奨される対応策

- **恒久対応案**: 最初のページ (`browser.pages()[0]`) と新しいページ、reload の直前の待ち時間などの手順を変えた使い回しの実験を、同じ負荷で 200 回以上行い、削除なしでの発生有無を確認します。
- **参考情報**: 最終仕様の「調査結果」の章の条件 3。
