# doxyfw 起動直後の Chrome で保存領域の値が失われる理由の調査 最終仕様

ファイル名: `261125-doxyfw-storage-loss-investigation-design.md`

## 目的と範囲

### 目的

puppeteer で起動した直後の Chrome で、文書の開始時に `localStorage.removeItem()` を実行し、その後に保存した値が再読み込みで失われる現象について、発生する条件の範囲を再現実験で特定します。結果は、将来 puppeteer で保存領域を扱うテストを書く人が、避けるべき条件を知るための調査報告として残します。

### 既知の事実

- 環境: Oracle Linux Server 8.10 (WSL)、Chrome for Testing 153.0.8010.36 (headless)、puppeteer 25.11.0、Node.js v24.21.0、`file://` のページ。
- 負荷あり (`taskset -c 0,1` で CPU を 2 コアに絞り、同じ 2 コアで空ループを 4 本動かす) で、1 回ごとにブラウザーを起動し、文書の開始時に削除してから保存と再読み込みを行うと、60 回中 24 回値が失われました。削除しない場合は 60 回中 0 回でした。削除スクリプトは再読み込みで再実行されていません。
- 同じ負荷で、ブラウザーを使い回す最小の再現用スクリプトでは、最初の文書で書いた `sessionStorage` の値が再読み込み後に読めない回が 200 回中 4 回ありました。

## 実験環境

### Chrome の版

| 版 | 入手元 | 配置先 |
| --- | --- | --- |
| 153.0.8010.36 | 導入済み (`/usr/local/bin/chrome`) | `/opt/chrome-for-testing/153.0.8010.36/chrome-linux64/chrome` |
| 取得時点の Stable の最新版 | Chrome for Testing の公開配布 | セッションの一時ディレクトリ |

Stable の版は、実験の開始時に公開一覧 `https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions.json` の `channels.Stable.version` を読んで確定します。取得元は `https://storage.googleapis.com/chrome-for-testing-public/<版>/linux64/chrome-linux64.zip` です。取得した zip は、セッションの一時ディレクトリの `cft-<版>/` へ置いて展開します。`/opt` への配置、`/usr/local/bin/chrome` の変更、環境変数 `PUPPETEER_EXECUTABLE_PATH` の変更は行いません。puppeteer には `executablePath` で展開先の `chrome` を渡します。

> [!NOTE]
> 2026-11-25 20:48 JST の時点で、Stable は 158.0.8127.88 でした。この版の zip (約 208 MB) を一時ディレクトリへ取得し、headless での起動と puppeteer 25.11.0 からの起動を確認済みです。実験の開始時に Stable が同じ版であれば、取得済みのものを使います。

取得に失敗した場合 (ネットワークの不通、配布物の欠落、起動の失敗) は、実験を始めずに作業を止め、全体管理文書の該当の WBS 項目をブロック中にして、ユーザーに扱いを確認します。

### 負荷

すべての試行を、既知の事実と同じ負荷の下で行います。

- 空ループ 4 本を `taskset -c 0,1` で CPU 0 と 1 に固定して起動します (例: `taskset -c 0,1 sh -c 'while :; do :; done' &` を 4 回)。
- 実験スクリプトを `taskset -c 0,1 node <スクリプト>` で起動します。Chrome の子プロセスは CPU の割り当てを引き継ぎます。
- 実験の終了後、空ループをすべて停止します。

同時に実行する実験スクリプトは 1 本だけとします。

### ページ

| 種類 | 内容 |
| --- | --- |
| `file://` | 一時ディレクトリの静的な HTML (`<!doctype html><title>t</title><p>t</p>` 相当) |
| `http://` | 同じ HTML を、Node.js の標準の `http` モジュールで書いた簡易サーバーが `127.0.0.1` で配信 |

### スクリプトの置き場所

再現実験のスクリプト (最小の再現スクリプト、条件を切り替えて繰り返す実行スクリプト、`http://` 用の簡易サーバー) は、セッションの一時ディレクトリ (`<スクラッチパッド>/261125-doxyfw-storage-loss-investigation/scripts/`) にだけ置き、リポジトリには追加しません。最小の再現コードは、調査報告に載せます。

## 試行の手順

### 共通

1 回の試行は、保存したキーの値を再読み込み後に読み、保存した値と一致しなければ「値が失われた」と判定します。試行の途中で例外やタイムアウトが起きた回は、値が失われた回とは区別して件数を記録し、有効な試行の件数が規定の回数に達するまで試行を追加します。

### 削除の時点の条件

| 条件 | 操作の順序 |
| --- | --- |
| 条件 1 (文書の開始時) | `page.evaluateOnNewDocument()` で削除スクリプトを登録、`page.goto()` (`load` まで待つ)、`page.removeScriptToEvaluateOnNewDocument()` で解除、保存、`page.reload()` (`load` まで待つ)、読み取り |
| 条件 2 (読み込み完了後) | `page.goto()` (`load` まで待つ)、`page.evaluate()` で削除、保存、`page.reload()` (`load` まで待つ)、読み取り |
| 条件 3 (削除なし、対照) | `page.goto()` (`load` まで待つ)、保存、`page.reload()` (`load` まで待つ)、読み取り |

削除と保存と読み取りは、保存領域ごとに `removeItem`、`setItem`、`getItem` を使います。条件 1 では、削除スクリプトの実行回数を `page.exposeFunction()` で Node.js 側に数え、再読み込みで再実行されていないことを毎回記録します。

### 起動方式

| 起動方式 | 内容 |
| --- | --- |
| 1 回ごとに起動 | 試行ごとに `puppeteer.launch({ executablePath, args: ['--no-sandbox'] })` で起動し、最初のページで手順を行い、試行の後にブラウザーを閉じる |
| 使い回し | 条件ごとに 1 回だけ起動し、試行ごとに `browser.newPage()` で新しいページを開いて手順を行い、試行の後にページを閉じる |

`localStorage` の「1 回ごとに起動」では、値が失われた回に、同じブラウザーで新しいページを開いて同じキーを読み、開き直したページでも失われているかを補足として記録します。判定には使いません。

## 条件表と試行回数

### localStorage

起動方式は「1 回ごとに起動」だけです。

| 削除の時点 | 版 | ページ | 試行回数 |
| --- | --- | --- | --- |
| 条件 1 | 153、Stable | `file://`、`http://` | 各 60 回。60 回で 1 回も発生しなければ 200 回まで追加 |
| 条件 2 | 153、Stable | `file://`、`http://` | 各 60 回。60 回で 1 回も発生しなければ 200 回まで追加 |
| 条件 3 | 153、Stable | `file://`、`http://` | 各 200 回 |

### sessionStorage

| 起動方式 | 削除の時点 | 版 | ページ | 試行回数 |
| --- | --- | --- | --- | --- |
| 1 回ごとに起動 | 条件 1、2、3 | 153、Stable | `file://`、`http://` | 各 200 回 |
| 使い回し | 条件 1、2、3 | 153、Stable | `file://`、`http://` | 各 200 回 |

条件の数は、`localStorage` が 12、`sessionStorage` が 24 です。試行の合計は 6,080 回から 7,200 回です。

> [!NOTE]
> 負荷なしの予備実行では、1 回ごとに起動する方式で 1 回あたり約 0.4 秒から 0.5 秒でした。負荷ありでは長くなるため、全体で数時間かかる見込みです。

### 判定の基準

| 結果 | 判定 |
| --- | --- |
| 規定の回数で 1 回以上値が失われた | 再現した (発生回数と回数を記録) |
| 規定の回数で 1 回も値が失われなかった | 再現しない (回数を明記し、「発生率が約 3 / 回数 以下と推定」と添える) |

条件の比較から、次の観点で結論を述べます。

- 版による違い (153 と Stable)
- ページの種類による違い (`file://` と `http://`)
- 削除の時点による違い (条件 1、2、3)
- 保存領域による違い (`localStorage` と `sessionStorage`)
- `sessionStorage` の起動方式による違い (1 回ごとに起動と使い回し)

結論は、実験で得た事実だけを述べます。内部の原因についての推測は、推測であると明記して分けます。

## 既知の不具合報告の検索

実験の後に、条件の比較で得た特徴 (再現した条件と再現しなかった条件) を検索語に使い、Chromium の不具合トラッカーの既知の報告を検索します。検索語には、ユーザーの個人情報とリポジトリ名を含めません。該当の判断は、報告の再現条件がこの調査の再現した条件と一致するかで行います。

```javascript
  // see: <報告の URL>
```

該当する報告が見つからない場合は、`page_link_probe.js` を変更しません。コメントのそのほかの文言と、関数の動作は変更しません。

### 結論

#### 事実

- 版による違い: 153.0.8010.36 と 158.0.8127.88 で、再現した条件と再現しなかった条件が一致し、発生率も同程度でした。Stable でも解消していません。
- ページの種類による違い: 値が失われたのは `file://` だけです。`http://` (`127.0.0.1`) では、同じ手順の全条件で 0 件でした。
- 削除の時点による違い: 値が失われたのは、文書の開始時に削除した条件 1 だけです。読み込み完了後に削除した条件 2 と、削除しない条件 3 では、`file://` を含めて 0 件でした。
- 保存領域による違い: `localStorage` と `sessionStorage` の両方で、条件 1 かつ `file://` のときに発生しました。
- `sessionStorage` の起動方式による違い: 1 回ごとに起動でも、使い回しでも発生しました。使い回しでも、新しいページごとに条件 1 の手順を行えば発生します。起動方式に依存しないため、「起動直後のブラウザー」固有の現象ではありません。
- 「規定の回数で発生しなかった」条件は、200 回で 0 件のため、発生率は約 1.5% 以下と推定されます。
- 既知の事実 (本章の前の節) の `sessionStorage` の使い回しで、削除なしの手順でも 200 回中 4 回失われた観測は、この実験の条件 3 (`file://` と `http://`、各 200 回) では再現しませんでした。その観測のスクリプトの手順がこの実験の最小の手順と異なる可能性があり、この案件では原因を特定していません (残課題一覧に記録)。

#### 推測 (実験で裏付けていない)

- 文書の開始時の `removeItem` が、保存領域の読み込みの完了前に実行された場合に、その後の保存が永続化されない状態になる可能性があります。`file://` は `http://` と、保存領域の取得の経路が異なる可能性があります。Chromium のソースは読んでおらず、内部の原因は未確認です。

#### 影響と回避策

`file://` のページに対して、文書の開始時に保存領域を削除してから保存する構成は避けます。保存値を消す必要があるテストは、読み込み完了後に `page.evaluate()` で削除すれば、この実験の条件では発生しませんでした (条件 2)。`page_link_probe.js` の `newReportPage()` の現在の構成は、削除を `clearVariant` を指定したページに限っており、この結論と矛盾しません。

### 既知の不具合報告の検索

検索日時: 2026-11-26 03:59 JST から 04:05 JST (WebSearch 4 回。検索語の例: 「Chromium bug file:// localStorage removeItem at document start then setItem lost after reload」「Chromium DOM storage sessionStorage localStorage file URL write lost after reload Page.addScriptToEvaluateOnNewDocument removeItem race」)。

該当する報告は見つかりませんでした。再現条件が近い報告として、Chromium の issue 40540194 (`https://issues.chromium.org/issues/40540194`、localStorage の移行処理が不整合な状態を残し `removeItem` が正しく動かない問題。M61 で修正済み) が見つかりましたが、移行処理が原因の別の問題であり、`file://` と文書の開始時の削除に限って再現する今回の条件とは一致しないため、該当としません。このため、`page_link_probe.js` は変更していません。

### 最小の再現コード

1 ファイルで、`file://` の最小の HTML を一時ディレクトリへ作成して実行します。負荷として、`taskset -c 0,1 sh -c 'while :; do :; done' &` を 4 本起動してから、`taskset -c 0,1 node minimal_repro.js <chrome> 40` で実行します。この環境で 153.0.8010.36 を使うと 40 回中 5 回で失われました (発生率は負荷と環境で変わり、上の表の実験スクリプトでは約 50% でした)。

```javascript
// 使い方: taskset -c 0,1 node minimal_repro.js <chrome の実行ファイル> [試行回数]
// 事前に taskset -c 0,1 sh -c 'while :; do :; done' & を 4 本起動する。
const puppeteer = require('puppeteer');
const fs = require('fs'), os = require('os'), path = require('path');
(async () => {
  const dir = fs.mkdtempSync(path.join(os.tmpdir(), 'repro-'));
  const file = path.join(dir, 'index.html');
  fs.writeFileSync(file, '<!doctype html><title>t</title><p>t</p>');
  const url = 'file://' + file;
  const n = Number(process.argv[3] || 100);
  let lost = 0;
  for (let i = 0; i < n; i++) {
    const browser = await puppeteer.launch({ executablePath: process.argv[2], args: ['--no-sandbox'] });
    const page = await browser.newPage();
    const s = await page.evaluateOnNewDocument(() => localStorage.removeItem('k')); // 文書の開始時に削除
    await page.goto(url, { waitUntil: 'load' });
    await page.removeScriptToEvaluateOnNewDocument(s.identifier);
    await page.evaluate(() => localStorage.setItem('k', 'v'));
    await page.reload({ waitUntil: 'load' });
    if ((await page.evaluate(() => localStorage.getItem('k'))) !== 'v') lost++;
    await browser.close();
  }
  console.log(`lost ${lost} / ${n}`);
})();
```

### 報告用の下書き

> 題名: localStorage / sessionStorage の値が、文書の開始時の removeItem の後に保存すると、file:// のページの reload で失われる (CPU 負荷が高いとき)
>
> 環境: Oracle Linux 8.10 (WSL2)、Chrome for Testing 153.0.8010.36 と 158.0.8127.88 (headless)、puppeteer 25.11.0、Node.js v24.21.0。
>
> 再現手順: 上の最小の再現コードを、CPU 2 コアに固定し、同じ 2 コアで空ループ 4 本を動かして実行する。
>
> 期待される結果: reload 後も、保存した値が読める。
>
> 実際の結果: 153 の `localStorage` で 60 回中 32 回、Stable (158) で 60 回中 30 回、値が失われる。`sessionStorage` でも、200 回中 62 回から 96 回で失われる。失われた `localStorage` の値は、同じブラウザーで開き直したページでも読めない。
>
> 発生しない条件: 同じ手順で `http://` のページ (200 回ずつ)、削除を読み込み完了後に行う手順 (200 回)、削除を行わない手順 (200 回) では発生しない。
>
> 補足: 内部の原因は未確認 (Chromium のソースは読んでいない)。報告の送信はユーザーが別途判断する。
